| **졸업·수료** | 졸업요건, 졸업논문, 영어/정보인증, 조기졸업 | Q10–Q18 |
| **휴학·복학·학적** | 휴학 한도, 복학 절차, 휴학 중 신분 | Q19–Q23 |
| **수강·성적·학점인정** | 최대 수강학점, 계절학기, 타대 학점, 재수강 | Q24–Q28 |
| **소속·학제개편** | 개편 전후 소속·요건 | Q33–Q35 |

**대상 입학연도**: 2021 / 2024 / 2026
**기준 학기**: 2026-2

### 1-2. 범위 밖 (답하지 않고 '확정 불가'로 처리)

| 유형 | 이유 | 평가셋 |
|---|---|---|
| 개인 심사·선발 결과 | 공개자료로 확정 불가 | Q29 |
| 미공개·미래 정보 | 근거 없음 | Q30 |
| 교수·담당자 재량 영역 | 규정 외 | Q31 |

> **범위 밖은 '실패'가 아니라 '정상 동작'입니다.** 화면에서도 오류가 아니라 정상 결과로 표시합니다.

## 2. 담당자 최소 입력 항목

### 2-1. 원칙
**담당자에게 두 개만 받는다.** 나머지는 시스템이 학적 DB에서 가져온다.
입력이 많아지면 쓰지 않게 되고, 자기보고가 늘면 hoBIT이 지적한 '미검증 입력 전파' 문제가 생긴다.

### 2-2. 입력 (담당자가 타이핑하는 것)

| # | 항목 | 필수 | 비고 |
|---|---|---|---|
| 1 | **문의 내용** | ✅ | 학생이 물어본 그대로. 자유 텍스트 |
| 2 | **학번** | ✅ | 이걸로 아래를 전부 조회 |
| 3 | 기준일 | ✗ | 기본값 = 오늘. 과거 기준 판단이 필요할 때만 변경 |

### 2-3. 자동 조회 (담당자가 입력하지 않음)
학번으로 학적 DB에서 가져온다 → `schemas/student_profile.json`

`입학연도` · `학과` · `학적상태` · `학년` · `전공유형` · `전과·편입 여부` · `누적 휴학 학기` · `이수학점` · `인증 충족 여부`

### 2-4. 보완 입력 (B 분기에서만)
시스템이 "이것만 더 필요하다"고 지목한 항목만, **그 자리에서** 추가로 받는다.
전체 폼을 미리 보여주지 않는다. (hoBIT의 on-demand 방식)

예: *"복수전공 상대 전공이 무엇인지 확인이 필요합니다"* → 한 칸만 열림 → 입력 → **같은 문의 ID로 재개**

## 3. 화면이 표현해야 할 처리 상태

| 상태 | 화면 |
|---|---|
| `idle` | 입력 대기 |
| `running` | 진행 중 + **실행 기록이 한 줄씩 쌓임** (학생 조건 확인 → 자료 검색 → …) |
| `A_draft` | 답변 초안 + 근거 패널 + 실행 기록 + [수정] [완료 저장] |
| `B_need_info` | 확인 필요 항목 + 보완 입력칸 + [재개] |
| `C_undetermined` | **확정 불가** + 사유 유형 + 판단자료 + 다음 행동 + [완료 저장] |
| `error` | 오류 + [재시도] |

> `running` 중 실행 기록을 보여주는 게 중요합니다. 몇 초간 빈 화면이면 담당자는 멈춘 줄 압니다.
> 그리고 그 기록 자체가 "무엇을 보고 답했는가"의 증거라 **평가 포인트**이기도 합니다.

## 4. 현선님께 확정 요청할 API 계약

화면을 짜려면 이게 먼저 고정돼야 합니다. **제안이며, 바꾸실 거면 말씀 주세요.**

```
POST /api/inquiry
  body: { question: string, student_id: string, as_of?: "YYYY-MM-DD" }
  →    { inquiry_id, ...answer_result.json }

POST /api/inquiry/{inquiry_id}/resume          # B 분기 보완 후 재개
  body: { answers: { "<항목키>": "<값>" } }
  →    { inquiry_id, ...answer_result.json }

POST /api/inquiry/{inquiry_id}/review          # 초안 수정 / 완료 저장
  body: { action: "save" | "edit", text?: string }
  →    { ok: true, status }

GET  /api/student/{student_id}   → student_profile.json
GET  /api/evidence/{chunk_id}    → chunk_metadata + 본문
GET  /api/inquiries?status=...   → 처리 이력
```

응답 본문은 `schemas/answer_result.json` 을 따릅니다.

### 4-1. 두 가지만 정해주시면 됩니다
1. **진행 상황을 어떻게 보낼지** — 한 번에 응답(동기) / 스트리밍(SSE) / 폴링
   → 동기로 하면 화면이 단순합니다. 다만 느리면 빈 화면이 길어집니다. **우선 동기로 만들고, 느리면 바꾸는 쪽**을 제안합니다.
2. **B 분기 보완 항목의 키 이름** — 예: `"major_type"`, `"target_major"` 같은 식별자
