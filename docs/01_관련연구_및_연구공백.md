## 1. 문제 정의

대학 학사 문의에는 다른 도메인 QA와 구별되는 성질이 둘 있다.

**(P) 프로필 의존성** — 같은 질문이라도 학과·입학연도·전공유형에 따라 정답이 다르다.
**(T) 시점 의존성** — 규정은 개정되며, 개정 전 입학생에게는 경과조치가 적용된다. 신청 절차는 학기마다 다르다.

두 성질 때문에 "의미가 비슷한 문서를 찾아 요약한다"는 표준 RAG 가정이 깨진다.
의미적으로 가장 가까운 문서가 **그 학생에게는 적용되지 않는 문서**일 수 있고, 이때 시스템은 틀린 답을 자신 있게 내놓는다.

이 문서는 선행연구를 (P), (T), 검색 방식, 에이전트 구조, 평가의 다섯 갈래로 나누어 검토한다.

## 2. 관련 연구

### 2.1 대학 학사 도메인 RAG — 프로필 축 (P)

#### 2.1.1 hoBIT / proFILL — 가장 가까운 선행연구
> Kim, Lee, Kim, Kang (2026). *hoBIT: A Profile-Aware Retrieval-Augmented Chatbot for University Academic Advising.* arXiv:2608.26604. 고려대 정보대학.

**한 것**
- 학사 상담 질문이 **profile-dependent** 하다는 문제를 정식화. 프로필을 모르는 검색기는 "그럴듯하지만 적용되지 않는 근거"를 낸다고 지적
- **오프라인 프로필 인덱싱**: 5속성 스키마(학과 / 전공유형 / 학년 / 입학연도 / 학적상태)로 각 청크에 "이 청크가 유효한 프로필 값"을 LLM이 주석. 적용범위와 무관한 속성은 null
- **정적/동적 인덱스 분리**: 규정은 정적, 공지는 동적. 질의 시 병합
- **on-demand adaptive profiling**: 로그인·전체 프로필 요구 없이, 질의 의도와 1차 검색 결과를 보고 **필요한 필드만** 역질문
- BGE-M3 + RRF, 오픈웨이트 모델로도 유효(온프레미스 가능). 인간 선호도 조사 포함

**남긴 것 (논문이 직접 적은 한계 포함)**
- ⛔ **시간 축이 없다.** 5속성 어디에도 개정일·시행일·대상학기가 없다. 정책 개정 누적은 "FAQ 유지보수가 어렵다"는 서술로만 등장하고, 해결되지 않는다
- ⛔ **프로필이 자기보고이며 기관 검증이 없다.** 논문 Limitations: *"잘못된 입력(예: 부정확한 입학연도)이 검색 결과로 전파된다"*
- ⛔ **단일 단과대(정보대학) 한정.** 프로필 스키마는 기관마다 재설계 필요
- ⛔ **학생 직접 응대형.** 근거가 불충분할 때 담당자에게 넘기는 경로가 설계에 없다

#### 2.1.2 국내외 일반 대학 챗봇
- 국내: RAG 기반 대학정보 QA 시스템(2025), SLLM+RAG 교육기관 문서 QA(**섹션 기반 파싱 + 표 데이터 처리** 제안), 대학 LMS 질의응답 챗봇, Education-specific RAG QA
- 해외: Springer 리뷰 논문, UPN Veteran Yogyakarta(LLaMA 3.1) 등. 보고 성능 예시 — Faithfulness 0.91, 범위 밖 질문 거부 81.25%

**남긴 것**: 대부분 "문서 넣고 답하기" 구조로, **적용 대상도 적용 시점도 구분하지 않는다.**
→ 우리가 넘어야 할 기준선은 이 그룹이 아니라 **2.1.1(hoBIT)** 이다.

### 2.2 시간·버전 인지 검색 — 시간 축 (T)

학사 도메인에는 없지만 **법률·세법 도메인에서 집중적으로 연구된** 영역이다.

| 연구 | 한 것 |
|---|---|
| *Temporal Misgrounding in Legal RAG* (arXiv:2608.09393) | 버전별 코퍼스 벤치마크 구축. 법적 정답은 **날짜 조건부 이진 판정**이며 "비슷하게 맞는 버전"은 오답이라고 규정 |
| *TimelyRAG* (arXiv:2609.11572) | 의미 유사도 + **조문 단위 시간 적합성** 결합. 질의에서 as-of 날짜를 추출해 유효기간으로 하드 필터링 |
| *VersionRAG* (arXiv:2510.08109) | 문서 버전 추적을 검색에 내장. 한계로 대규모 버전 이력 확장성·버전 입도 문제 인정 |
| *Asking For An Old Friend* (arXiv:2605.23497), *When Do LLMs Apply the Wrong Law?* (arXiv:2608.14610) | 법령 QA에서 LLM의 시간 관련 실패 유형 진단 |
| *Ontology-Driven Graph RAG for Legal Norms* (arXiv:2505.00039) | 규범 구조를 그래프로 표현 |

**인용 가치가 가장 높은 수치** (arXiv:2608.09393, *전문으로 재확인 예정*):
> 11개 모델에서 파라메트릭 지식 strict accuracy 평균 3.0%, 현행본 정적 코퍼스 RAG 2.7%.
> **정적 RAG가 날짜상 적용되는 버전을 검색한 비율 0%.**

**남긴 것**
- ⛔ **전부 법률·세법 도메인.** 대학 학사 규정에 적용한 사례를 조사 범위에서 찾지 못했다
- ⛔ **사용자 속성 조건이 없다.** 법령은 "언제"만 따지면 되지만, 학사는 "언제 × 누구"다
- ⛔ 학사 특유의 **입학연도 기준**(개정과 무관하게 코호트로 고정되는 축)이라는 개념이 없다

### 2.3 검색 방식 — 하이브리드와 메타데이터

- *A Hybrid Approach to IR and Answer Generation for Regulatory Texts* (arXiv:2502.16767): 파인튜닝 임베딩 + BM25 하이브리드가 단독 방식 대비 Recall@10·MAP@10 유의하게 상회. 규정 텍스트는 전문용어·유의어·환언 때문에 어휘 검색만으로도 의미 검색만으로도 부족
- RRF (Cormack et al., SIGIR 2009) — 단순하고 강건한 융합. hoBIT 채택
- BGE-M3 (arXiv:2402.03216) — 다국어·dense/sparse/multi-vector 통합 임베딩
- 메타데이터 필터링이 아키텍처 변경보다 검색 정확도 기여가 크다는 보고 (업계 벤치마크, **1차 출처 확인 필요**)

**함의**: 정리본 §4의 "정확한 교과목명·규정명은 키워드 검색 병행" 판단은 문헌과 일치한다. **Qdrant 하이브리드 선택에 근거가 있다.**

### 2.4 에이전트형 RAG — 자기교정 루프

과제 요건은 "RAG 시스템"이 아니라 **"AI Agent 앱"** 이다. 이 구분을 뒷받침하는 계열.

- *Agentic RAG: A Survey* (arXiv:2501.09136), *Reasoning RAG via System 1 or System 2* (arXiv:2506.10408): 정적 파이프라인 → **의사결정 루프**로의 전환. 질의 이해·계획, 도구/검색 오케스트레이션, 다중홉 분해, **자기성찰**의 네 능력
- **Self-RAG**: 생성 도중 스스로 추가 검색을 결정하고 초안을 비판
- **CRAG (Corrective RAG)**: 경량 평가기가 검색 품질에 신뢰도를 매기고, 낮으면 질의 재작성 등 교정 전략 발동
- **Adaptive-RAG**: 질의 난이도에 따른 경로 라우팅
- *Self-MedRAG* (arXiv:2601.04531): 의료 QA에 자기성찰 하이브리드 RAG 적용 — **고위험 도메인 적용 선례**

**함의**: 정리본 §6의 루프 —
> 문의 분석 → 조건 확인 → 검색 → **검증 → 부족하면 검색 범위 조정 또는 추가 정보 요청** → 근거 갖춰지면 초안

— 은 CRAG/Self-RAG 계열의 자기교정 루프와 구조가 같다. **"왜 RAG가 아니라 Agent인가"에 대한 답이 이미 설계에 들어 있다.** 다만 문헌 용어로 명명되어 있지 않을 뿐이다.

**남긴 것**
- ⛔ 교정 루프의 **종료 조건**이 대개 "검색 품질 점수"다. 우리처럼 **"적용 조건이 검증되었는가"** 를 종료 조건으로 삼은 사례는 보지 못했다
- ⛔ 루프가 실패했을 때의 출구가 대개 "웹 검색으로 확장" 이지, **사람에게 이관**이 아니다

### 2.5 평가 방법론

- **RAGAS** (arXiv:2309.15217): Faithfulness / Answer Relevancy / Context Precision / Context Recall. 참조 정답 없이도 상당 부분 측정
- hoBIT: DeepEval + 인간 선호도 조사

**남긴 것**
- ⛔ 위 지표는 전부 **"답을 했을 때 얼마나 잘했나"** 만 본다
- ⛔ **답하지 않기로 한 판단의 적절성**(적절 이관 / 과잉 이관)을 재는 표준 지표가 없다. 고위험 행정 도메인에서는 이게 핵심 안전 지표인데도 그렇다

## 3. 연구 공백

### 3.1 공백 매트릭스

| | 프로필 축 (P) | 시간 축 (T) | 사람 이관 | 도메인 |
|---|---|---|---|---|
| hoBIT / proFILL | **O** | ✗ | ✗ | 대학 학사 |
| 법률 RAG (TimelyRAG, VersionRAG 등) | ✗ | **O** | ✗ | 법률·세법 |
| 일반 대학 챗봇 | ✗ | ✗ | ✗ | 대학 학사 |
| 에이전트형 RAG (Self-RAG, CRAG) | ✗ | ✗ | △ | 범용 |
| **학사나침반 (제안)** | **O** | **O** | **O** | **대학 학사** |

### 3.2 공백 1 — P × T 교집합이 비어 있다
hoBIT은 *"2024학번 AI 심화트랙에게 적용되는 요건"* 은 풀지만,
*"그 규정이 2023년에 개정되었고 기존 입학생에게는 경과조치가 있다"* 는 다루지 않는다.
법률 RAG는 정확히 그 반대다.
**두 축을 동시에 조건으로 거는 연구를 찾지 못했다.** 그런데 학사 도메인에서는 두 축이 항상 함께 작동한다.

### 3.3 공백 2 — 프로필이 검증되지 않는다
hoBIT이 스스로 적은 한계다. 자기보고 입학연도가 틀리면 그대로 전파된다.
또한 **학점 합계·요건 충족 같은 수치 판정을 벡터 검색 결과로 수행하면 안 된다**는 점이 선행연구에서 명시적으로 다뤄지지 않는다.

### 3.4 공백 3 — 모르면 어떻게 할 것인가에 대한 설계가 없다
선행 사례는 전부 "답한다"를 전제한다. 거부율을 보고하는 연구는 있지만, **거부 이후의 업무 흐름**(판단자료 생성 → 담당자 이관 → 처리 상태 추적)을 설계한 사례는 없다.
행정 도메인에서 틀린 답의 비용은 "불만족"이 아니라 **졸업 지연·신청 기한 상실**이다.

## 4. 우리의 기여 — 공백에 대한 대응

| # | 기여 | 대응 공백 | 근거 설계 |
|---|---|---|---|
| **C1** | **3축 메타데이터 스키마** — 입학연도 / 개정일·시행일 / 대상학기를 분리하고, 예외·경과조치를 연결 | 공백 1 | 정리본 §2, §3 |
| **C2** | **학적 DB 연계 검증** — 프로필을 자기보고가 아닌 DB 조회로 확정. 학점·마감 판정은 벡터가 아닌 **구조화 계산** | 공백 2 | 정리본 §4 |
| **C3** | **3분기 응답 설계** — 근거 충분→초안 / 정보 부족→선택적 역질문 / 불명확→**판단자료 생성 후 담당자 이관** | 공백 3 | 정리본 §6 |

**보조 기여 (C4)**: P×T가 갈리는 지점만 모은 **평가셋과 ablation 설계**. strict/느슨한 정확도의 격차로 두 축의 필요성을 정량 입증 (`04_평가셋_설계.md`)

### 4.1 한 문단 요약 (발표·제안서용)
> 대학 학사 질의응답에서 정답은 학생 속성(P)과 적용 시점(T) 모두에 의존한다.
> 선행연구는 둘 중 하나씩만 다뤘다 — hoBIT은 프로필 축을 인덱스 구조로 끌어올렸으나 시간 축이 없고, 법률 RAG는 시간 축을 다루지만 사용자 조건이 없다.
> 본 과제는 두 축을 **동시에 조건으로 거는 검색**을 학사 도메인에 적용하고, 프로필을 학적 DB로 **검증**하며,
> 근거가 확보되지 않을 때 답을 만들어내는 대신 **판단자료와 함께 담당자에게 이관**하는 업무용 에이전트를 제안한다.

## 5. 그래서 우리가 더 해야 할 일

### 5.1 선행연구에서 **그대로 가져올 것** (재발명 금지)
- [ ] LLM 청크 주석 + **null 규약** (hoBIT §2.1) — 적용범위 결정 속성만 채우기
- [ ] **정적/동적 인덱스 분리** (hoBIT) — 규정 vs 공지
- [ ] **Intent routing** (hoBIT) — 인사·잡담을 검색 전에 차단
- [ ] **점진적 프로필 수집** (hoBIT) — 단, 우리는 "DB에 없는 것만" 묻는 형태로 변형
- [ ] **BGE-M3 + 하이브리드 + RRF** (hoBIT, arXiv:2502.16767) — 스택 논쟁 종료
- [ ] **섹션 기반 파싱 + 표 처리** (SLLM 논문) — 교육과정 표에 직접 필요. **전문 확보 필요**
- [ ] **CRAG식 검색 품질 평가 후 재검색** — 단, 종료 조건을 "적용 조건 검증 완료"로 교체

### 5.2 **우리가 새로 만들어야 할 것**
