# 사용자 확정 — 직원용 업무 시스템

- 작성일: 2026-10-02 / 작성: 신기훈
- 근거: 2026-10-02 14:58~14:59 팀 결정

> **노현선**: "전 행정실, 과사 등 학교 직원이 쓰는 걸로 생각하긴 했어요.. **업무용 에이전트니까**"
> **신기훈**: "그럼 직원이 맞을듯"

이 결정이 기존 문서에 미치는 영향과, 그 결과 **강해지는 것 / 약해지는 것**을 정리한다.

---

## 1. 한 줄 정의

> **학생이 쓰는 안내 챗봇이 아니라, 과사 직원이 학생 문의에 답할 때 쓰는 업무 도구다.**

학생은 **문의의 출발점**이지 시스템 사용자가 아니다. 시스템은 어떤 경우에도 학생에게 직접 회신하지 않는다.

---

## 2. 이 결정으로 **강해지는 것** 4가지

### 2.1 고려대와 사용자가 완전히 다르다 → 중복 소멸
hoBIT은 학생 직접 응대형이다. 우리가 직원용이면 **같은 도메인이지만 사용자·목적·화면이 전부 다르다.**
"비슷한 거 아니냐"는 질문에 대한 답이 간단해진다.

### 2.2 개인정보 문제가 사라진다 ★
학생용이었다면 **학적 DB 조회가 심각한 문제**였다.
- 본인 확인을 어떻게? 로그인은? 타인 학번 입력하면?
- hoBIT이 자기보고 프로필에 의존한 이유가 바로 이것이다 (논문 윤리 섹션: 세션 한정 보유, 영구 DB 없음)

**직원용이면 이 문제가 통째로 없어진다.** 직원은 원래 업무상 학생 학적을 조회하는 사람이다.
→ **우리 기여 C2(학적 DB 검증)가 실현 가능해지는 조건이 바로 직원용이라는 점이다.**
→ 즉 hoBIT의 한계(자기보고 미검증)는 **학생용이기 때문에 생긴 구조적 한계**이고, 우리는 사용자를 바꿔서 그걸 푼다. 이건 꽤 좋은 논증이다.

### 2.3 "업무용" 요건이 명확해진다
과제 Category G는 **업무용** AI Agent를 요구한다. 직원용이면 해석 논란이 없다.

### 2.4 AI2L 순수형이 된다 (용어가 깔끔해짐)
- 기존: HITL(AI가 받고 예외만 사람) + AI2L 혼합
- 변경: **AI2L 단일** — 사람이 주행위자, AI는 근거를 모아 보조

> 발표 한 문장: **"사람이 결정하고, AI는 근거를 모읍니다. (AI-in-the-Loop)"**

---

## 3. 이 결정으로 **약해지는 것 / 조심할 것** 3가지

### 3.1 ⚠ 학생 대기시간이 직접 줄지 않는다
현선님 원래 동기는 "전화 연결이 어렵다"였다. 그런데 직원용이면 **학생은 여전히 전화한다.**

→ 발표에서 **"학생 대기시간 감소"라고 단정하면 반박당한다.**
→ 정확한 주장: **"직원 1건 처리시간 단축 → 통화 회전율 상승 → 간접 완화"**
→ 이 편이 측정도 쉽다 (03 문서 §4-2 자체 측정)

### 3.2 ⚠ "③ 담당자 이관"의 의미가 바뀐다
직원이 이미 사용자이므로 **넘길 담당자가 따로 없다.** ③분기는 이제 이렇게 재정의된다.

| 기존 | 변경 |
|---|---|
| 담당자에게 이관 | **"공개자료로 확정 불가" 표시 + 판단자료 제시** |
| — | 사유 유형 표시: `근거없음` / `자료충돌` / `최신성불명` / `재량영역` |
| — | 다음 행동 제안: 학과 확인 / 상위부서 확인 / 학생에게 추가 질문 |

**이게 오히려 더 좋다.** AI가 "모르겠으니 사람한테" 하는 게 아니라, **"여기까지는 확인했고, 여기서부터는 확정이 안 된다"** 를 보여주는 것이기 때문이다. 문헌(Alibaba 에스컬레이션 유형 분류, arXiv:2605.14830)의 아이디어를 그대로 쓸 수 있다.

### 3.3 ⚠ 시연이 덜 화려해진다
학생이 말 걸고 답 나오는 게 보기에는 좋다. 직원 화면은 상대적으로 밋밋하다.
→ **대응**: 시연을 "질문→답변"이 아니라 **"같은 질문, 다른 학번 → 다른 근거"** 를 나란히 보여주는 쪽으로 구성한다. 평가셋 Q07/Q08이 그 용도다.

## 4. As-Is 재서술 — 직원 관점

사용자가 바뀌었으니 as-is도 직원 기준으로 다시 쓴다. (03 문서의 학생 관점 서술과 병행)

1. 전화·방문·메일로 문의 접수
2. 학생 신원·학번 확인 → **학적 시스템에서 조회**
3. 질문 유형 파악 (졸업요건 / 복수전공 / 휴학 …)
4. **규정집에서 해당 조문 찾기** ← 병목
5. **그 학생 입학연도에 어떤 버전이 적용되는지 판단** ← 가장 어려운 지점
6. 해당 학기 공지·일정 확인
7. 애매하면 학과·상위부서 확인 → 회신 지연
8. 구두 또는 메일 회신. **기록은 대부분 남지 않음**

**직원의 진짜 병목은 4~5다.** 조문을 찾는 것보다 **"이 학생에게 어느 버전이 적용되는가"** 를 판단하는 게 오래 걸리고, 틀리면 비용이 크다.
→ 우리 C1(3축 메타데이터)이 정확히 이 지점을 겨눈다. **사용자를 직원으로 바꾸니 기여와 병목이 더 정확히 맞물린다.**
