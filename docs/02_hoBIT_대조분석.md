## 1. hoBIT이 실제로 한 것 (원문 §2 기준)

### 1-1. 프로필 스키마 — 5개 속성
> The default profile schema comprises five attributes: **department, major type, grade, admission year (admission cohort), and student status.**

### 1-2. 오프라인 인덱싱
- 코퍼스 5종: **규정 PDF / 오리엔테이션 PDF / 학과 웹페이지 / 게시판 공지 / 담당자가 작성한 FAQ**
- 청킹 후 **LLM이 각 청크에 프로필 레코드를 주석**: 그 청크의 적용 대상을 결정하는 속성만 값을 채우고, 무관한 속성은 **null**
- → non-null 필드가 그 청크의 "프로필 의존 적용범위"이자 "검색에 필요한 사용자 속성"이 됨
- **정적 인덱스 / 동적 인덱스 분리**: 갱신 빈도 기준 (규정 → 정적, 공지 → 동적). 질의 시 양쪽 결과 병합

### 1-3. 온라인 질의 처리
- **Intent routing** 5종: greeting / ability / faq / smalltalk / **retrieval**. retrieval만 검색 단계로
- **On-demand adaptive profiling**: 로그인·전체 프로필 요구 없음. 질의 의도로 필요한 필드 판정 → 없는 것만 역질문
- 1차 검색 결과를 **다시 보고**, 적용 가능성 확인에 추가 필드가 필요하면(예: 장학금 세부 자격) 그때 추가 질문 → 세션 프로필 갱신 → 재검색
- 세션 프로필은 **시간 제한**이며 이후 폐기, 영구 사용자 DB 없음

### 1-4. 스택·평가
- BGE-M3 임베딩, RRF 융합, DeepEval, 인간 선호도 조사
- 오픈웨이트 모델로도 유효 → 온프레미스 운용 가능

## 3. 결론 — 세 문장으로 정리한 우리 포지션

1. **hoBIT은 "누구에게 적용되는가"(프로필 축)를 인덱스 구조에 넣었다.**
   우리는 거기에 **"언제부터 적용되는가"(시행일·경과조치)와 "어느 학기 기준인가"(대상 학기)** 를 더한다.
   → 2축 → **3축 확장**

2. **hoBIT은 프로필을 학생 자기보고에 의존하며 이를 논문이 직접 한계로 적었다.**
   우리는 **학적 DB 조회로 프로필을 검증**하고, 학점 합계·마감 판정은 벡터 검색이 아니라 **구조화된 계산**으로 분리한다.
   → 검증되지 않은 입력의 전파 차단

3. **hoBIT은 학생에게 바로 답한다.**
   우리는 **근거가 충분하면 초안, 부족하면 추가 확인, 불명확하면 담당자 이관** — 고위험 행정 도메인에 맞는 3분기 설계다.
   → 과제 요건의 "업무용" 과도 일치

## 4. hoBIT에서 **가져올 것** (바퀴 재발명 금지)

- [ ] **LLM 청크 주석 + null 규약**: 적용범위를 결정하는 필드만 채우고 나머지는 null. 그대로 쓰면 됨. 우리는 여기에 시간 축 필드를 추가
- [ ] **정적/동적 인덱스 분리**: 규정은 정적, 공지는 동적. 현선님 정리본 1장 E의 "학기별 공지" 처리에 바로 맞음
- [ ] **Intent routing**: 인사·잡담·능력질문을 검색 전에 걸러내면 비용과 오답이 동시에 줄어듦
- [ ] **점진적 프로필 수집**: 전체 폼을 미리 받지 않고 필요한 것만 묻기. 우리는 학적 DB가 있으므로 "DB에 없는 것만" 묻는 형태로 변형
- [ ] **BGE-M3 + RRF**: 같은 도메인 같은 언어에서 검증된 조합. 스택 논쟁 종료
