## 2.6 사람 개입형(HITL) 행정 AI — 직원이 주인공인 시스템

### 2.6.1 CARE — 가장 가까운 구조적 선례
> *Transforming public administration workflows with multi-agent AI: A human-in-the-loop knowledge orchestration framework.* ScienceDirect (CARE: Council Agents for Response and Engagement)

**한 것**
- **공공행정의 문의-응답 업무**(inquiry-response workflow)를 대상으로 한 사람 개입형 멀티에이전트 시스템
- 고위험 행정 프로세스에 생성형 AI를 넣기 위한 **사회기술적 아키텍처** 제안
- 설계 축 3개: **추적가능성(traceability)**, **제한된 자율성(bounded autonomy)**, **기관 역할 모델링(institutional role modeling)**

**우리에게 주는 것**
- 우리 과제와 **업무 형태가 같다**(민원·문의 접수 → 근거 확인 → 회신). 학사행정은 그 하위 사례
- "제한된 자율성" 은 우리가 말하는 **3분기 설계**(답변/역질문/이관)의 상위 개념. 용어를 빌려 쓸 수 있다
- ⚠ 공공기관 대상이며 대학 학사 적용 사례는 아님 → **우리 자리는 남아 있다**

### 2.6.2 HITL vs AI2L — 우리가 어느 쪽인지 정하는 구분
> *Human-in-the-Loop AI: A Systematic Review of Concepts, Methods, and Applications.* MDPI Entropy (2026)

| 모델 | 구조 | 예 |
|---|---|---|
| **HITL** (Human-in-the-Loop) | **AI가 주행위자**. 자율 처리하다가 예외·저신뢰 건만 사람에게 **에스컬레이션** | 고객센터 봇 |
| **AI2L** (AI-in-the-Loop) | **사람이 주행위자**. AI는 보조 도구 | 전문가 업무 보조 |

**우리는 둘 다 쓴다.**
- 학생 문의 1차 선별 = **HITL** (AI가 받고 애매하면 올림)
- 담당자 화면 = **AI2L** (담당자가 결정하고 AI는 근거를 모아줌)

> 발표에서 이 두 용어를 쓰면 "챗봇 아님"을 한 문장으로 설명할 수 있다.
> **"저희는 HITL로 접수하고 AI2L로 처리합니다."**

### 2.6.3 에스컬레이션의 실증 연구
> *Agentic AI and Human-in-the-Loop Interventions: Field Experimental Evidence from Alibaba's Customer Service Operations.* arXiv:2605.14830

**한 것**
- AI 처리 가능 건 **11,069건**을 대상으로 한 현장 실험. 에스컬레이션을 **유형별로 분류**
- 모니터링 알고리즘이 "AI 능력 범위를 넘는 문의"를 감지해 **알고리즘 주도 에스컬레이션** 발생

**우리에게 주는 것**
- **"언제 사람에게 넘길 것인가"가 독립된 연구 주제**라는 근거. 우리 C3를 곁다리가 아니라 본론으로 세울 수 있다
- 에스컬레이션 **유형 분류**라는 아이디어 → 우리 이관 사유를 `근거없음 / 자료충돌 / 최신성불명 / 재량영역` 으로 나누는 설계에 쓸 수 있다
- ⚠ 커머스 고객센터 도메인. 행정 규정 적용 판단과는 성격이 다름

### 2.6.4 기타
- *Automating Document Intelligence in Statutory City Planning* (arXiv:2603.13245) — 법정 도시계획 문서 자동화. **행정 규정 문서 처리**라는 점에서 인접
- *A Case for Humans-in-the-Loop: Decisions in the Presence of Erroneous Algorithmic Scores* (arXiv:2002.08035) — AI가 틀렸을 때 사람이 교정 가능한가. **우리 시스템이 틀릴 수 있다는 전제를 다루는 근거**
- *Decision-Making with Human-in-the-Loop: A Field Experiment of Explained AI in Public Administration* — 설명 제시가 행정 의사결정에 미치는 영향

**2.6 전체의 남긴 것**
- ⛔ 대학 학사행정에 HITL 프레임을 적용한 사례를 찾지 못했다
- ⛔ 이들 연구에는 **시간 축(규정 개정·경과조치)** 개념이 없다 → 우리 C1은 여전히 고유하다

## 2.7 챗봇이 아닌 UI — 근거를 앞에 내세우는 인터페이스

### 2.7.1 대화형 vs 그래픽 인터페이스 비교
> *Comparing LLM-Based Conversational and Graphical Interfaces for Industrial Decision Tasks: An Exploratory Mixed-Methods Study.* arXiv:2605.31224

**현선님 판단("챗봇이면 안되겠다")을 직접 뒷받침하는 유일한 문헌.**
업무 의사결정 과제에서 대화형 UI와 그래픽 UI를 비교한 연구다.
→ **전문 확보 1순위.** 발표에서 "왜 챗봇이 아닌가"의 근거로 쓸 수 있다.

### 2.7.2 Provenance(출처)를 인터랙션의 중심에 둔다
> *SpheriCity: Designing Trustworthy Conversational AI for Sustainability Decision Support.* arXiv:2606.13854

**한 것**
- 전문가는 **합성된 주장을 검증 없이 받아들이지 않으며**, 이해관계자에게 권고를 정당화하려면 추적 가능한 근거가 필요
- 따라서 **출처(provenance)를 주 인터랙션 루프 안에 전면 배치**. 응답마다 페이지 단위 인용을 임베드

**우리에게 주는 것**
- 담당자는 전문가다. **"답변 먼저, 출처는 접힌 채로" 가 아니라 근거가 화면의 주인공이어야 한다**
- 우리 정리본 §6의 "UI에 실행 기록과 출처를 보여준다"와 정확히 일치

### 2.7.3 검증을 돕는 화면 설계
> *VArify: A Visual Analytics System for Verifying Knowledge Enhanced LLM Responses.* arXiv:2606.10177

- 사용자는 **표만으로는 검색된 지식을 탐색하기 어렵다.** LLM 텍스트 응답과 근거 매핑을 정렬하지 못하고, 무엇이 관련 있고 신뢰할 만한지 추적하는 데 어려움을 겪는다
- → **맞춤형 센스메이킹 지원**이 필요

### 2.7.4 신뢰 UI 패턴 (업계 정리 — 1차 출처 아님, 참고용)
- 응답별 **신뢰도 표시**
- 불확실할 때 **되묻는 프롬프트**
- 사실 주장에 **출처 인용** — 스캔 가능하되 어지럽지 않게, 펼치면 검증 가능하게, **AI 본문과 시각적으로 구분**
- **추론 단계의 점진적 공개**(progressive disclosure)
- **능력 경계(capability boundaries) 명시**

**2.7 전체의 남긴 것**
- ⛔ 대부분 여전히 **대화형 전제**. 업무 큐·처리 상태를 가진 **워크플로우 UI** 연구는 드물다

## 3. 이 조사가 우리 설계에 주는 것

### 3-1. 현선님 판단에 근거가 생겼다
"행정업무 보는 사람 돕는 거니까 챗봇이면 안 되겠다" 는 직관이었지만,
→ **AI2L 모델**(사람이 주행위자), **CARE의 제한된 자율성**, **대화형 vs 그래픽 비교연구**가 모두 같은 방향을 가리킨다.

### 3-2. 고려대와의 차이를 한 문장으로
> hoBIT은 **학생에게 답하는 챗봇**이고, 우리는 **담당자가 판단하도록 돕는 업무 시스템**이다.
> 전자는 HITL의 앞단만 있고, 우리는 **앞단(접수·선별) + 뒷단(판단 보조·처리 기록)** 을 모두 만든다.

### 3-3. 새 공백 (공백 4)
> 학사행정에 **사람 개입형 업무 프레임**을 적용하고,
> **챗봇이 아닌 근거 중심 업무 화면**으로 구현한 사례가 없다.

## 4. 화면 요구사항으로 환산 (한준님·현선님께 넘길 것)

문헌에서 나온 것을 그대로 화면 요구로 바꾸면:

| # | 요구 | 출처 |
|---|---|---|
| U1 | **근거 패널이 주인공.** 답변 옆이 아니라 동급 또는 상위 배치 | 2.7.2 |
| U2 | 모든 사실 주장에 **조문·URL 단위 인용**, 본문과 **시각적으로 구분** | 2.7.2, 2.7.4 |
| U3 | **실행 기록(trace) 패널** — 학생 조건 확인 → 연도별 검색 → 공지 확인 → 적용 검증. 접었다 펼 수 있게 | 2.7.4, 정리본 §6 |
| U4 | **담당자 큐 화면** — 이관 건 목록 + **이관 사유 유형** + 자동 생성된 판단자료 | 2.6.1, 2.6.3 |
| U5 | 담당자가 **수정·반려·승인**할 수 있을 것 (권한이 사람에게 있음을 화면으로 표현) | 2.6.2 |
| U6 | **능력 경계 표시** — "이 질문은 공개자료로 확정 불가" 를 명시 | 2.7.4 |
| U7 | **자료 충돌 시 양쪽을 나란히** 보여주고 자동 선택하지 않기 | 정리본 §2 |
| U8 | 처리 상태 추적 (접수 / 자동응답 / 이관 / 완료) | 2.6.1 |

> **U4가 고려대에 없는 화면이다.** 시연 ③은 이 화면 없이는 보여줄 수 없다.
> 챗 UI는 U1~U3만 있으면 되지만, 우리는 U4~U8이 있어야 "업무용"이 된다.
